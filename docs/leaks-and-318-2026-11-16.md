# 宿主内存口径 + 闲置 zcode-cli 回收 + 3.18.2 适配评估（2026-11-16）

### 事故：webui 开不了，界面停在「未能收到启动状态」

用户报「webui 很久开不了，提示 startup 有问题」。现场取证（不是 3.12 引导协议回归，
`startup-channel-unavailable` 出现 0 次）：

- `zcode-host` VmRSS 1.01GB，**VmSwap 2.21GB** → 实际工作集 3.17GB；整机 15.5GB RAM 用 11.5GB、
  swap 10.2GB **100% 满**、空闲只剩 183MB。
- server 进程 `D`（`folio_wait_bit_common` 等页 I/O），`/api/health` 8.7s~10s 超时，页面入口要 **40s**
  才跑到 JS，浏览器 perf 里 RPC 往返 **6~7s**。
- 渲染层的 30s 启动期限因此被击穿 → 官方启动失败页
  `未能收到启动状态。请退出并重新打开 ZCode…`（`startup.global.error.startup_status_timeout`）。
- 现场还抓到「ws 升级失败 → HTTP 回退」那次 **45 秒零下行帧**（perf `in=0f`，`perfIn` 在 http 路径
  有埋点，所以是真的没收到），同样落到 30s 超时；用户连刷三次页面才靠 ws 起来。
- 内存守卫只读 `VmRSS`（`src/memory-guard.mjs:129`），宿主 1014MB < kill 线 1238MB →
  **139 次 WARN、0 次回收**，3.17GB 的工作集对守卫完全不可见。

### 两类泄漏（都是官方宿主侧的，垫片只能从外面收拾）

1. **agent app-server 不退出**：每次页面连接，宿主拉起一批 `zcode-cli`（实测一次 2×400MB +
   5×200MB ≈ 1.8GB），页面关闭后 **0 CPU 挂几小时**。官方只在桌面 transport dispose（stdin EOF，
   见 `zcodeStdioTransport.ts`）时收掉它们，web 会话永远不触发。两天手机刷新累积 17 个（985MB RSS +
   swap），是这次 swap 打满的直接推手。它们都是宿主的**孙子进程**（`zcode-host → 直连 CLI 监督进程
   → 每附着一批 turn/agent 运行时`）。
2. 宿主自身 watcher/流缓冲增长：`mem-attribution` 里 `FSWatcher=8042→8630`、external 尖峰 +671MB
   （11-09 事故同源）。

### 修复 1：内存守卫改按 **RSS + VmSwap** 判

`src/memory-guard.mjs` 新增 `sampleHostFootprintMb()`（VmRSS + VmSwap），`decideMemoryAction()`
一律用 `footprintMb`（`rssMb` 仍上报，`hostSwapMb` 新增）。阈值语义不变（还是 warn 6% / kill 8% /
hard 20%，本机 929/1238/3096MB），但**被换出的页也算内存**——否则「RSS 看起来正常、实际 3.2GB」这种
形态永远不触发。11-16 的真实数字回放：RSS 口径只 warn，footprint 口径命中 hard 上限 → 回收。
`/api/health` → `guards.memory.hosts[]` 现在带 `rssMb/swapMb/footprintMb`。

### 修复 2：闲置 agent CLI 回收器（`src/agent-proc-reaper.mjs`）

server 每个 `REAP_INTERVAL_MS`（60s）tick 一次，**全部条件同时满足**才 SIGTERM：

- 全局 busy-guard 说空闲（`agentWorkActive()`：模型请求 / tasks-index running / CLI DB 写 /
  进程树 CPU 探针）；
- 该会话**没有附着 view**且**没有新鲜 presence 租约**（页面真的不在了）；
- 是 `zcode-host` 的后代且 **depth ≥ 2**（绝不碰宿主与它的直连监督进程，这两个是「基础附着」）；
- `comm` **精确等于 `zcode-cli`**（`zcode-node-repl` 是工具运行时，同样大小但不碰；
  bash/python/node 更不碰）；
- 存活 ≥ 5min，且**整棵子树**在 10min 窗口内 CPU tick 一个都没变（有忙子进程=有回合）；
- 每 tick 最多 8 个，深的先跳过（选中祖先即覆盖子树）。

代价只是下一次页面连接重新 spawn 一个附着运行时，不丢历史（2026-11-16 手工杀 17 个后实测：
页面照常加载、health 正常）。开关 `ZCODE_WEBUI_PROC_REAPER=off|dry-run|on`（默认 on），
`_MIN_AGE_MS`/`_IDLE_MS`/`_MAX_PER_TICK`/`_MIN_DEPTH`（minDepth 硬钳到 ≥2）。
日志 `[proc-reaper] SIGTERM idle agent cli pid=…`；`/api/health` → `guards.procReaper`
（mode/config/ticks/reaped/lastPids/history）。

自检：`node scripts/dev/agent-proc-reaper-test.mjs`（18 项，全合成快照 + 假 killer：深度/comm/
年龄/子树忙/cooldown 式状态机/回收上限/回收 pid 复用）；
`node scripts/dev/memory-guard-test.mjs`（新增 6 项 footprint 回放）。真机 dry-run
（`/tmp/reaper-live-check.mjs` 那种写法）在 11-16 的树上精确命中 6 个 200MB 的 `zcode-cli`，
不含 `zcode-node-repl`。

# 补记（同日）：3.18.2 的凭据加密桥 —— 卡死真因与修复

## 症状复现（沙箱）

`ZCODE_SERVER_RUNTIME_ROOT=~/.zcode/server-3.18` + 3.18 渲染层，页面 `body.zcode-startup-ready`
出现、`#root` 恒为 1683B 的 `root-startup-loading`，等 110s 不画、无 JS 报错。埋点后确认渲染层的
`isRestoringOAuthSession` 一直是 true：`esr()` 的恢复 effect 走到
`await oauthService.restoreCachedSessionState()` 就再没回来。

## 真因

`RPC-in oauth.restoreCachedSessionState` 到达宿主后没有 `RPC-out`。`async_hooks` 打出长期挂起的
promise 创建栈：`initializeHostApiNetworkTransportOwner → establishOwner → createLocalServices →
ProviderRuntime.start → configRuntime.start()`。

3.18 的宿主按 Electron **utilityProcess** 设计：凭据加解密不在进程内做，而是
`credentialCipherProvider = vx(e => parentPort.postMessage({type:'credential-cipher-request',…}))`，
等 `{type:'credential-cipher-result', requestId, result:{ok, value|error}}`。
本项目 `src/port-shim.mjs` 把 `process.parentPort` 桥到 fork IPC（`{__z:'pp', msg}`），
而 server 的 pp 分支只认 `database-startup-state` / `log` / 冒烟控制行 —— 这类请求被静默丢弃，
于是 `configRuntime.start()` 永远不就绪，凭据读不出来，登录态恢复挂死。

排除过的假设：Secret Service/keyring（本机没有，且进程无 dbus fd）、文件锁
`credentials.json.lock`（删掉锁仍挂）、v1→v2 迁移（离线预迁移成 v2 仍挂）、scoped-service-port。

## 修复

- `src/credential-cipher.mjs`：官方 headless 密钥派生
  `sha256(ZCODE_CREDENTIAL_SECRET ?? 'zcode-credential-fallback:'+platform+':'+homedir+':'+username)`，
  AES-256-GCM，信封 `enc:<v>:<scheme>:` + `base64url(iv).base64url(tag).base64url(ct)`；
  能读 `enc:v1:`（≤3.17 写的），新写 `enc:v2:env:`；`enc:v2:os:` 明确报
  `CREDENTIAL_SECURE_STORAGE_UNAVAILABLE`。附 `ensureCredentialBackup()`。
- `src/host.mjs`：pp 分支遇到 `credential-cipher-request` 就地应答并把
  `credential-cipher-result` 发回宿主；`createHost16` 在宿主支持该桥时先确保备份。
- 删掉中间尝试过的 `src/credential-bridge.cjs` preload（port-shim 会覆盖 `process.parentPort`，
  preload 无效，别再用这个思路）。

## 验证

- 沙箱（3.18.2 运行时 + 渲染层 + 生产 v2 数据副本）：
  `cipher decrypt ok (key source: env)`；三标志全部落下；`ui-boot-check`：startup-ready 8.2s、
  root 281221B、composer=1、任务列表渲染；`credentials.json.bak-pre318` 自动生成。
- 离线：`node scripts/dev/credential-cipher-test.mjs`（16 项：信封往返、v1 兼容、纯文本透传、
  错误码、请求/应答形状、密钥派生式、备份路径）。

## 新登录协议结论（不需要额外垫片）

渲染层登录按钮 → `window.open('https://zchat.z.ai/auth?…redirect_uri=…zcode://oauth/callback…')`
→ 宿主 `oauth.startOAuthWithPolling`（实测 OK 652ms，`pollIntervalMs=2000`）→ 宿主每 1–2s
`oauth.pollPendingOAuth` 收口。`zcode://oauth/callback` 深链只是桌面端的快速路径，
垫片的 `onOAuthCallback` 保持 no-op 订阅即可；轮询完成时渲染层自己跳转登录态。
唯一 UX 待办（可选）：官方中转页会尝试 `zcode://` 深链，浏览器无法处理——可在浮层里提示
「认证完成后直接回到本页即可」，或后续补一个粘贴回调地址的兜底。

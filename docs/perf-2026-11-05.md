# 2026-11-05：resume 回退 http、渲染层 RPC 崩溃、shim 性能埋点

起因：用户报控制台里
`subagentsStore-BF3iXtI0.js:3 Uncaught TypeError: Cannot read properties of undefined (reading '0')`
（栈：`me.onBuffer` ← `onMessage` ← `_.fire` ← `MessagePort.handler`），并说「zcode-webui 最近很卡顿」。

结论：**这条报错和「卡」是同一个 bug 链的一环**，另外还有官方渲染层自身的老毛病（超长 transcript 全量渲染）。
下面每一段都在生产日志里有对应证据，或做过 A/B 复现。

---

## 一、报错根因（日志闭环）

1. 空闲/后台掉线：`[ws] client unresponsive (no pong for 2 ping(s))` → `[ws] DETACHED`。
2. 页面热重连 `resume=1`。服务端 `attachView()` 里**先补发停靠期缓存的帧**（`prevView.resumeBuf`），
   `readyLine` 由调用方（`wss.on('connection')` / `/bridge/open`）在 `attachView` **之后**才发。
   于是这条 ws 的**第一条消息是二进制帧**，而不是 ready 控制行。
3. `web/bootstrap.js` 的 `onmessage` 把「第一条消息不是 ready」判成 `unexpected ws peer`
   → `ws.close()` → `startHttpMode()`。**每一次带回放的 resume 都白掉进 http 长轮询**。
   - 日志：91 次 `POST /bridge/open` 里 62 次带 `resume=1`，`[view] resume replay` 51 次，二者对齐；
     单次回放可达 **3733 帧 / 1.8MB**（`[view] resume replay tab=6e51d476: 3733 buffered frame(s), 1828260B`）。
4. http 传输下，服务端 `/bridge/open` 的**第一帧就是 readyLine**：
   ```json
   {"kind":"zcode-webui-ready","startupMode":"runtime","startupId":"zcode-webui-<uuid>"}
   ```
   实测**正好 115 字节**，与日志里 `lastDelivered: 115B:7b226b696e64223a227a636f64652d77…`
   （`{"kind":"zcode-w`）完全一致。
5. 旧 `parseHttpFrames` 只认已知 kind：`handleControlText()` 对 ready 返回 false → 落到
   `deliverToRenderer()` → 官方 RPC 客户端用 `new re(e)` 解析 JSON，`n = E(t)` 得 `undefined`，
   随后 `n[0]` 抛 `Cannot read properties of undefined (reading '0')`。
   - 日志：**56 次**该报错全部 `transport=http`，其中 13 次 `lastDelivered` 就是那条 115B 控制行。

### 修复（全部在 `web/bootstrap.js`，刷新页面即生效，不需要重启服务）

- `parseHttpFrames`：以 `{`（0x7b；RPC 帧首字节恒为 0..6）开头的载荷**一律按控制行消费**，
  未知 kind 也只记日志，**绝不投给渲染层**；并且**不再 `return`**。
  旧代码遇到"已知"控制行直接 return，会把同一批 poll 里**后面所有帧**静默丢掉
  （「不刷新就看不到最新状态」的隐蔽来源之一）。
- `handleControlText`：认识 `zcode-webui-ready`（顺带取 `startupMode`/`startupId`），
  并把 `zcode-webui-*` 命名空间下**所有**未知控制行一并消费——以后服务端加新控制行也不会再毒到渲染层。
- ws `onmessage`：ready 之前的二进制帧进缓冲（上限 8192 帧 / 32MB），收到 ready 后按序补投，
  再 `flushUplink()`；只有**静默** 3s（每来一帧就重置计时）既没有帧也没有 ready 时才判定对端不是我们、
  回退 http。于是 resume 回放不再触发 `unexpected ws peer`。
- `?transport=http` 现在**真的强制** relay：以前它落进 `maybeStartHttpMode()` 的 CONNECTING 重试阶梯，
  本地 ws 9 秒内打开就静默赢了，开关形同虚设（也让这次的 A/B 做不出来）。
- 顺带修一个每帧开销：`noteDelivered()` 以前会顺手 `window.__zb_debug = true`，于是页面出现**任何**
  一次 console.error 之后，**每一帧**都走 `noteDelivered + console.debug`（devtools 打开时特别贵；
  该用户页面正好有 56 次报错 × 25~40 帧/s）。现在调试日志只由 `?zbdebug=1` 打开，环形缓冲只记录。

### A/B 实证

`node scripts/dev/perf-collect.mjs --transport=http --legacy-bootstrap=<旧构建>`（同一页面、同一后端，
只用 Playwright `context.route` 替换 bootstrap 文件，不动 `web/`）：

| 构建 | 结果 |
|---|---|
| 旧（HEAD） | `pageerror: Cannot read properties of undefined (reading '0')`，shim 自己 `console.debug` 打出那条 115B 控制行 |
| 新（本提交） | 0 错误，页面功能完整（打开会话 + 滚动都正常） |

## 二、「卡」的实测数据

### 埋点（`web/bootstrap.js` 顶部 perf 块，默认开启、低开销）

- 每帧：只做计数器自增（帧数/字节/first byte/最大帧/top5 大帧/每秒桶）。
- 长任务：被动的 `PerformanceObserver({entryTypes:['longtask']})`。
- 每 30s 报一次时跑一个 **6s 的 rAF 采样窗**（20% 占空比，不做常驻 rAF 循环），
  得 p50/p95/max 帧间隔与 >50/100/250ms 的 jank 计数。
- 同时记：heap（`performance.memory`）、DOM 节点数、poll 次数与 RTT、ws 打开/回退/重连次数、
  pre-ready 缓冲帧数、控制行丢弃数。
- 上报：**一行** `kind=perf` 到服务端 `/api/log`，所以
  `grep '| perf |' zcode-webui.log` 就是**用户自己那台设备**的时间线。
- 主动接口：`window.__zwebui_perf()`（快照对象）、`__zwebui_perf_sample(ms)`（Promise<fps>）、
  `__zwebui_perf_report()`、`__zwebui_perf_reset()`。

### 采集脚本

```bash
node scripts/dev/perf-collect.mjs                     # 60s，ws
node scripts/dev/perf-collect.mjs 90                  # 90s
node scripts/dev/perf-collect.mjs 60 --transport=http # 强制 relay
node scripts/dev/perf-collect.mjs 60 --open-task=sess_xxx --scroll=10000
node scripts/dev/perf-collect.mjs 30 --legacy-bootstrap=/tmp/bootstrap-old.js   # A/B
```

只读：只开页面、可选点开一个会话、从不发 prompt。打生产（3102）需 `ZOOM_TEST_ALLOW_PROD=1`。
输出 `/tmp/zwebui-perf-<ts>.json` + 摘要，检测到 `reading '0'` 崩溃时退出码 1。

### 本机实测（headless Chromium 1440×900，打生产 3102；会话 `sess_4976e3f7`，库里 2.7MB / 1180 part）

| 场景 | 结果 |
|---|---|
| 首屏 | 93 帧 / 1.5MB；5 个长任务共 1074ms，**最大 450ms** 主线程阻塞；最大帧 248kB |
| 点开会话 | 点击→响应 219ms；随后 8s 再 28 帧 / 2.1MB；7 个长任务 1385ms，**最大 575ms**；单帧最大 **780kB** |
| 会话打开后空闲 | 很干净：rAF p50 16.7ms，0 jank |
| **滚动长会话** | **p95 116.8ms、max 250ms；41 帧 >50ms、27 帧 >100ms；32 个长任务共 3776ms / 10s** |
| DOM 形状 | 滚动容器 14177~23868px 高、**8229~10349 个节点**（2653 span / 1960 svg path / 313 LINK），**没有虚拟化** |
| http relay 下每条带帧的 poll | RTT p50 **756ms**（对比 ws 直推）——所以「resume 掉进 http」本身就是体感卡的一环 |

**结论**：卡的主体在**官方渲染层**（超长 transcript 全量渲染 + 每次开/换会话 0.4~0.6s 主线程长任务），
不在传输层（空闲时 16.7ms 满帧、帧流量很小）。垫片侧能做的是：别再把页面踹到 http 长轮询、
别让一次报错把每帧都变成 `console.debug`。渲染层内部的虚拟化缺失是黑盒，垫片修不了；
想要体感变好，现实手段是别让单个会话无限长、别在超长会话里频繁来回切换。

### 另一处「卡」来源（host 侧，与渲染层无关）

host 对厂商 API 的调用会整段超时失败：

- `usage-stats.getCodingPlanResetStatus` → `ApiError: fetch failed`，
  实测 **15567ms / 10497ms / 10456ms / 5066ms**（页面一加载就调它：11:09:34 attach → 11:09:35 FAIL）；
- `marketing-touch.query` 5891ms、`client-scenes.list` 5057ms。

表现是「打开页面后某块面板/额度信息很久才出来」。`src/api-cache-guard.cjs` 目前覆盖
`billing/(balance|current)`、`quota/limit`、`subscription/list`，**不含**
`/api/v1/coding-plan/reset/status`；若超时继续高频出现，可把该路径加进
`ZCODE_WEBUI_BILLING_CACHE_PATTERN`（改 preload 需重启服务）。

## 三、版本现状（排查时确认）

`/api/health` → `hostVersion: 3.16.3`，页面注入 `rendererVersion: 3.16.3`；而
`zcode-update.sh` / `src/upgrade.mjs` 的 `PINNED_VERSION`、`SHIM_MAX_SUPPORTED` 仍写 **3.15.3**，
`vendor/renderer` 时间戳是 10-29（与 3.16 适配的那串 commit 同期）。
也就是说本机实际跑在**超出 shim 声明支持上限**的 3.16.3 上。是否把钉位更新到 3.16.3（或固定回 3.15.3）
需要用户确认，本轮未改。

## 四、遗留与后续

- 服务端 `attachView()` 仍在 ready 行之前补发回放（协议上「控制行先到」并不成立）。客户端已容忍，
  且缓冲有上限；要彻底理顺需要把 `attachView` 拆成「记账」+「回放」两步，让 ws 分支在注册监听器之后
  先发 ready 再回放。**本轮未做**（改动面大、收益小），留档待后续。
- 3.16.3 的钉位/文档不一致（见上）。
